# Source18 UV contract audit and inactive source19 recipe

Status: **a real UV/material import mismatch is confirmed**, independently of the known official GLES native-Skin tangent packing/decoding bug. This is not a causal attribution of the earlier silver-grid screenshots and not an art acceptance. Frozen source18 GLB `afb966396bf5ad656b3cb0cd2edc388fc6fa02eba59df8b81d9a23ac53f3be8b` is unchanged. No GPU run, render, replacement GLB or new editable mother was generated by this audit.

## Actual imported data, not guessed names

`uv_audit/import_receipt.gd` reads actual Godot4.6.3 imported material parameters and mesh position/UV arrays. `compare.py` pairs451 sampled imported vertices against the exact GLB position+UV0 (error below1e-4). Sixteen armor surfaces specify TEXCOORD_1 for base/normal/ORM, but the standard material samples UV0. Both cloth wraps specify TEXCOORD_2 for their normal; the standard material also samples UV0. Third UV data is retained in CUSTOM attributes by the importer, not globally lost; this standard material simply does not use it.

The armor base texture alone additionally specifies KHR scale(0.125,0.25), offset(0,0.75). Godot puts this into the material's global UV1 transform, which is applied before all base-UV samples. Thus base uses the wrong source coordinate, and normal/ORM use both the wrong source coordinate and the base-only transform. All401 armor samples mismatch their intended coordinates; all50 wrap-normal samples mismatch theirs. CPU bilinear/repeat probes find baseRGB max absolute difference0.328 and normalRGB0.777 (channels in0..1), not simulated GPU pixel differences. ORM usually differs little because much of it is flat: mean absolute channel error0.00128, despite the coordinate error.

Evidence: `docs/evidence/production-v2-uv-contract/source18-uv-contract.json` contains each affected surface's sample counts/errors, representative expected/actual UV and texture samples, source hashes and upstream references. Full raw receipts are preserved with recovery artifacts.

## Inactive editable source19 recipe

`prepare_source19.py` is dry-run by default and only accepts the exact source18 mother SHA. It leaves geometry, skin weights, skeleton, animation, palette and existing normals intact. For armor it promotes the real render UV to the single runtime UV0 after scale(1/8,1/4), retains the original base atlas unchanged, and repeats existing normal and ORM pixel tiles8x4 so all three textures can sample the same UV0 without a KHR transform. For wraps it promotes the real render UV (third source set) to runtime UV0. Original source UV layers remain in the frozen source18; a future written derivative has one unambiguous runtime UV set. Source layer choice is `active_render`, not merely the currently selected editor UV layer.

Read-only planning successfully covered all18 affected surfaces. The pure periodicity test verifies4096 negative/positive UV samples: bilinear base-level error below1.28e-14. **No written19 asset exists yet.** `--write-derived-source` is an explicit later step, held until the same-source actual Mobile/Metal control is complete. It must then be exported and checked for UV0-only texture contracts, tangent correctness, unchanged rig/weights/clip timing and actual GPU appearance. It does not fix the GLES engine bug.

Budget caveat: an exact standard-material tiling recipe expands each512² normal/ORM image to4096x2048. Shared tiling compresses well on disk but increases decoded/driver texture cost; mip behavior and cost are not validated. This is an editable correctness candidate, not an adopted final performance architecture. A later explicit multi-coordinate shader can preserve the original small images if judged appropriate, but is not implemented here.
