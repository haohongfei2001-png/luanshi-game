## 最新 Owner 规模纠正（2026-11-12；优先于本文旧文案）

**立刻读取 `docs/PRODUCT_DECISIONS.md §1L`。** Owner 不希望人为锁死战场面积或一场战争可存在的人数。**512v512 只是衡量最少 1024 名独立士兵能否同时在同一战斗实例持续存在/行动并按实际战况结算的性能验收场景，**绝非每场战斗固定人数、场景最大容量或必须 1024 人全部同屏。

- 河关一张地图是首个品质样板，不是最终世界里唯一能容纳战争的固定 MOBA 大小区域。实际战场范围由地理、双方军队位置、攻守目标及行军/突围决定，地图可按需更大或更小、分区加载、远处可靠持续仿真。
- 一场战斗可以几十、几百、上千乃至更多人；人数来自世界军籍和兵力部署、不会为满足 512v512 压测凭空刷兵，也不能超过 1024 就硬拒绝或删人。
- 远处士兵无须全部逐帧近景渲染、无须同时交战，但他们**必须实际存在**、保持身份/位置/命令/伤亡/装备，镜头外的时间与战事继续；镜头移动过去可自然恢复细节，禁止冻结或装饰假人。
- 仍然必须有 **512v512 的标准压力验收**与真实 M5 60 FPS 目标；这是**容量/性能最低可验证样本**，不能冒充无限硬件能力。用分层更新、共享小队 AI、LOD、地图流式加载等技术优先降低计算成本，报告真实设备规模上限和未知项。
- **不要为此推倒现有河关 PR 或改成开放世界工程**。在已经实现的战斗和世界/存档机制上修改硬编码人数/战场面积假设，新增大小规模/跨不同战线的回归；玩家体验和易用性继续第一。

## 一、最终交付：真正值得反复玩的 macOS 战斗首版

从**现有 Godot 4 项目和已制作的河关可玩候选**继续开发，不重新建仓库、不将历史可选内容当必做表格。以 Owner 真正关心的体验为验收核心：

1. **一次完整可玩的战争**：从正常启动进入战前部署和简单兵种/将领任务分派，实战中 WASD+鼠标瞄准+普攻+技能、骑马或战车、号角令旗/传令兵、可滑动镜头观察不同战线，到基于真实目标/军情的结算和战后随军、继续行军、休整与存读档，全部在**同一个正常游戏入口**连续可用，不靠开发命令或未连接的技术演示。
2. **按战役实际兵力与战场范围动态存在的军队**，标准压力样本为 512 对 512 名普通兵（同时保有 1024 个真实兵员身份，不含主角及额外军官/坐骑），各有持续身份、武器、攻击、防御、血量、士气和真实伤亡，视野内持续挥砍/格挡/射箭/溃逃，视野外仍有可信因果结算，回到原位置不能凭空复活或全体暂停。**普通兵可以低成本 FSM 和小队共享行动，性能优先。**
3. **九种可实际操作的武器**：剑、刀、棍、枪、长刀、弓、弩、剑盾、双剑。每种有相匹配的持握、动作、攻击范围、起手/后摇、Q/E/其他技能、命中与防守/反制，不能仅更换名称、图标或攻击数值。早期主角仍弱且可被杀，成长后在适当局面可累计杀数十普通兵，不把生命值膨胀成无敌。
4. **双方强将同样具有战斗力**：玩家不是独享英雄机制。敌我先锋、叫阵小将/精锐、分队将领、战场主将有独立武器战斗与统军行为；全军主帅可以留在后方、不在地图中。重要将领之间的战斗依靠可见动作、站位、时机、格挡/闪避、技能和反制；敌将会主动杀伤己方士兵/将领而非等玩家找他。受伤/被救、亲卫保护、撤离/被俘/阵亡、指挥继任有可信后果。**斩将不直接胜利。**
5. **真正的军事胜负**：各方战略目的、守点/攻门/护送/突围/救援、地形、战线、有效兵力、阵型、指挥链、预备队、士气、补给与撤退通路共同决定结果。固定“死亡达到 72% 即全局判定”只能作为局部士气/战力因素，不能一刀切。玩家战死结束该人生，但不能因此把存活友军从世界中删除或自动宣告对方取得整个战争的战略胜利。
6. **一张高品质战场优先，但不锁死面积和人数**：继续打磨河关地图/城门/道路/桥/坡/树林、战线、城门攻守、多个局部目标和真实物流干预，修正队伍拥挤、避碰/阵型、门楼遮挡、镜头/操作和关键战况可读性。**历史上的夜战、山林、火攻、海战、火炮等仅为灵感库**，仅选实际能明显提高乐趣又不显著增加复杂度的项目，其他允许不做。不要铺开二十张粗糙地图或让玩家管理大量粮袋/水井/弹药菜单。
7. **美术、动作、声音、UI 真实提升**：近景能看清脸、手、服装、甲胄与真正持握武器；远景能认出兵种、军旗、阵型与交战动作。优先角色姿态/武器打击、受击/倒地/骑乘、场景光影/材质、真正有辨识度的战争声音；不用生成概念效果图冒充实际 Godot 画面。UI 少、清晰、符合军事任务的实时操作，不堆满浮窗。
8. **MacBook Air M5 流畅目标**：现有托管 M1 巡场与 Linux llvmpipe 仅供参考，**不是目标真机 60 FPS 通过**。先使用现有合法云端 GPU/Metal/CI profiling，给出每档画质和内部渲染尺寸、帧时间 P50/P95/P99、输入延迟、内存、画面真实性与单位规模；迭代模拟 AI/路径、批量绘制、LOD、动画、遮挡、物理、阴影、镜头长帧。真实 M5 上 ≥20 分钟 512v512 连续交战属于独立设备门槛；未获授权访问该设备就标 `DEVICE_NOT_TESTED`，**不得阻塞其他不依赖真机的开发，也不得虚报完成**。不默默从 1024 降成几十兵或把人物变成没有伤害的布景。

**正式文学剧情、人物传记、婚恋与固定主要故事全部留空**；只允许军事任务和系统占位文字。用户日后自行创作。此前压缩千年历史的人生愿景保留，但战史库不再构成几十种玩法强制清单。

## 三、全程工作顺序：一次总授权，不需 Owner 每阶段再发令

### 阶段 A：恢复、整合与质量底座
- 全量对照现有 PR 的功能/依赖/失败 CI，消除重复和冲突；恢复并验证 Linux + 原生 Mac 包、合法字体与旧存档。
- 统一当前游戏入口、部署、战斗、结算、继续行军、存档。给出一份稳定的可玩集成候选与可回退 SHA。
- 不能为了改结构清空旧成果/删回归测试。涉及不确定内容时先建立最小可回放测试。

### 阶段 B：先处理最影响“玩得好”的质量缺陷
- 正面解决**冲车/城门/桥狭口拥挤、战线层次、目标可见性、交战接触/动画和近景遮挡**；敌我士兵与坐骑不得大规模叠在一起或持续穿模。
- 修正镜头跟随、侧滑、缩放、屋盖遮挡/半透明处理、视角切换与最重要战况/军令提示。优先改**玩家能立刻看见的**问题。
- 每项 UI/可玩性改动在实际 GUI 进行连续操作测试，保存真实 Godot 对比截图/录像，不能只写 HTML/视频概念示意。

### 阶段 C：九武器、角色与精锐敌将
- 逐一把九套武器的普攻与 Q/E/其余技能打磨成**实际动作、攻击判定、距离/节奏/反制、武器姿态**相互一致的玩法；弓弩有真实装填与投射。骑马/战车交互可读且有真实受损/接战限制。
- 提升人物的手、脸、衣甲与武器模型，动作不是同时摆臂的机械群众；视距 LOD/骨骼必须控制成本。
- 双边强将与玩家公平搏斗，叫阵小将/先锋/亲卫区别于一般士兵、将领有独立行动与护卫/被救/失能/继任。**看得出他们在影响战争，但不给一个 Boss 血条替代军队战争。**

### 阶段 D：真正的战略目的和易用统军
- 使战前任务、令旗/号角、将领自主作战、预备队、真实战况/后勤与城门争夺贯穿同一实战。玩家只做少数清楚、有价值的选择，将领/后勤在后台自动执行。
- **胜负综合态势**：敌帅死亡非自动胜利；双方有效军力、士气、指挥、目标、地形和补给决定夺城、护送、守时、撤退、被击溃/投降等。
- 在当前一张地图上尝试少数明显增强乐趣的地形/伏击/粮道或多点任务变体；若造成大量菜单/降低画质或性能，**合并或不做**。唐末—清朝战史全量是参考库，不必照搬。

### 阶段 E：性能、体验审核与打磨
- 固定实际场景，跑 20/100/250/512 每方普通兵的真实接战性能/镜头移动/攻城/密集箭雨/骑兵/长时间存读档/音频场景；记录 Linux software 与托管 M1 和目标 M5 的差别，不能从 M1 确认 M5。
- 进行多轮**完整可玩回放**：至少进攻破门胜利、撤退、主角阵亡，以及“将领阵亡但战争继续”“未斩将但目标完成”的可复现战例。
- 发现明显粗糙/不连贯/不耐玩就优先继续打磨，不因所有技术测试绿而停止。用真实游戏画面、操作轨迹、音效和性能数据评估；不要为了完成度扩大地图/兵种数量。
- 没有真机访问权限时仍要**做完可自测部分**。真正 M5 性能需要授权或 Owner 一次集中试玩才进入单独的设备门槛，清楚交付可执行测试包与已知限制。

### 阶段 F：正式可供 Owner 试玩的完整候选
- 统一一份清楚的 `Luanshi macOS battle V1 candidate` 可直接运行构建、独立的 SHA-256、版本/commit、简单操作说明、CI 和存档迁移证据、实际画面/带声录像，以及默认画质档/内部渲染尺寸与性能状态。
- 提供**一份简短的交付报告**：已完成的核心体验、未完成/待 M5 实测/未选用的历史候选、真正影响继续玩下去的前三个缺陷、明确下一开发动作。**不要每完成一个 PR 就要求 Owner 重新向 Codex 传话**。
- **通过标准**：集成游戏可以不看代码从头到尾连续打完真实千人战役，装备/武器和指挥有明显区别，战场动作/视觉清晰、真实伤亡并能接续原部队，普通士兵易用轻量 AI、双方强将与不同战略目标真的影响战局。M5 20分钟/60fps 未实测则独立列为 `M5_DEVICE_PENDING`，不称全面性能通过。
- 只有用户自己最终判断主观乐趣/设计质感是否满意。你不需提前反复请用户测试每个中间版本。
