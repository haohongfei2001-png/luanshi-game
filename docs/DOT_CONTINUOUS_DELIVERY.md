# Dot 持续自主开发协议（历史背景，已由 DOT_HANDOFF_FINAL.md 更新）

**请以 PRODUCT_DECISIONS.md、FINAL_GAME_DESIGN_SPEC.md、NARRATIVE_ART_DIRECTION.md、ACCEPTANCE_MATRIX.md、DOT_HANDOFF_FINAL.md 为当前权威来源。本文件保留以供历史参考，若冲突以上述最新文件为准。**

目的：让 Dot 从当前 GitHub 原型继续工作，不反复要求所有者讨论正常设计/技术细节，直到完成具有完整玩法与结局的 Mac 单机游戏。**这是一项长期目标，不代表保证无限自主运行，也不免除产品平台的权限/额度/暂停限制。**

## 执行权

- Dot 是**唯一默认日常实施者**：直接使用自身云电脑编辑 Godot、运行命令/测试、操作已有授权 GitHub、编写资源、维护计划。
- **不默认调用 Codex**；不调用用户 Mac 进行日常研发；需要前述两者必须先获得明确授权。
- 可以自主进行：代码与架构、无付费合法资源选择、剧情细节、UI、模型/动作占位与替换、重构、分支和 PR、自动化测试、文档、版本修复。
- 重大未经授权事项：花钱、连接额外账号/电脑、开启收费服务、正式对外商店发布/开源许可证、改写主人已定的核心游戏设定。需要审批时，给出**一个推荐默认选项 + 最小必要决策**，不要让所有者重新当项目经理。
- 仅公开与项目相关且合法可分发的内容；不得上传私密信息、密钥、未授权第三方资产。

## 与现有分支的衔接

当前已存在第一原型分支 `prototype/cloud-first-playable`、[PR #1](https://github.com/haohongfei2001-png/luanshi-game/pull/1) 及其真实测试记录。**继续利用现有代码，不从零重写。**
在后续阶段读取 main 最新的设计文档，并**正确 rebase/merge** 设计更新，避免覆盖已经交付的代码或用户新约束。

## 任务循环

1. 阅读本协议、`PRODUCT_DECISIONS.md`、`PRO_DESIGN_BIBLE.md`、`DELIVERY_PLAN.md` 和 `AGENTS.md`。
2. 查当前分支、未完成 PR、最近测试报告和阻塞；决定**最小下一可测试里程碑**。
3. 在自己的云电脑编码/构建/测试/验证/修复，形成 commit/PR/可运行产物，记录证据。
4. 如果阶段通过，**无需逐项征求批准就进入下一阶段**；只在“必须由所有者授权”的事项暂停相关操作。
5. 如果测试失败，先自主定位与修复；若云环境无 GUI，则如实记录无法验证视觉体验，在可完成的模拟/构建测试上继续推进，不用虚构合格结果。
6. 每次会话/任务结束前持久化：`docs/PROJECT_STATUS.md`（当前阶段、已通过、未通过、阻塞、下一个可执行动作）、GitHub commit/PR，防止上下文遗失。
7. 尝试使用 Dot 支持的持续任务或定期检查机制维持后续推进。若产品暂停、限额、审批卡住，则留明确状态并向所有者报告**具体阻塞**；不得承诺平台保证永不停止。
8. 不因达到“20 vs 20 原型”或“首次短篇”就自行宣布**完整愿景**已完成。须对照下述完成标准。

## 两层“完成”，避免混淆

- **第一个完整可玩版本**：拥有从开场到结局的战役，可在 Mac 上运行，有存读档、即时战斗、招募装备与物资、城池变动、有限情报、重要人物行为、主角死亡结算。可能是较小的地图和较短的内容，是可供试玩/发行的独立作品。
- **项目既定长期愿景**：上述机制进一步扩展到显著更大的乱世，角色经历较长人生，战斗从小队成长到军团，城池和政治变化更深。数十万/百万规模属于战略数据，独立同屏人数必须受验证与可读性约束。**不要把性能不切实际的百万 AI 同屏视作必要的完成条件。**

达到第一层后继续维持版本质量和按性能依据扩大范围；如果扩展代价已远超当前授权/资源能力，说明可实证限制并提出可行替代，不应无止境降低质量。

## 质量闸门

- 功能：可复现源代码、有测试/运行命令/真实日志；至少每个可玩版本生成下载包或可用试玩途径。
- 战争：角色动作、士兵移动/攻击/死亡/军令、胜负、伤亡、装备与库存不能相互矛盾。
- 世界：离屏战况、粮食、行军、消息延迟、NPC 自主行动和重要结局必须可追溯因果。
- 叙事：有始有终、多个实质性分支、死亡即结束、玩家只能看到可知的信息。
- 体验：可读 UI、可操作性、设置/教程、保存恢复、关键 bug、资源授权与分发合法性。
- macOS：云端构建 ≠ 在 M5 Mac 上实际玩过；两种证据分开保存。iOS、Apple 签名和正式商店发行是独立批准项目。

## 人类介入政策

默认不要请求每阶段讨论和批准。保留可运行成果供用户**主动**试玩与反馈；当真正准备正式发布或需要账户/资金/设备权限时再请求。用户是否喜欢战斗手感与美术，AI 没法通过自动测试作出最终权威判断；所以无人类反馈时只能标记“AI 验证通过，用户体验未确认”，不能假装用户已认可。

## 工作状态输出标准

每次成果说明只需：完成的游戏能力、真实测试证据、GitHub 链接、可玩产物、未验证事项、下一个自动执行步骤。不要把“写完文档”混同“游戏完成”。
