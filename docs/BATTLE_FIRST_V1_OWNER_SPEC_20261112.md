# 《乱世》首个正式可玩版：千人战场优先权威规格 v1.3
**用户亲自提出｜2026-11-12｜状态：OWNER LOCKED（目标） / Codex IMPLEMENTATION**
本文件优先于本仓库早期的“20v20 为第一阶段的最终规模”“先交 1–3 小时剧情短篇”“Dot-only、Codex 禁止默认调用”等过时安排。**不是已经实现的功能或已经通过的性能测试。** 对已有游戏、测试、存档与长线世界设计的其他不冲突规定继续有效。

## 0. 唯一目标与禁止误解

**Codex 在 Godot 现有工程基础上，尽最大工程能力把《乱世》的初版核心战斗做到实际可玩、成熟、精致，尽可能接近 Owner 的完整愿景，而不是实现一份形式上的功能清单。**

- **初版目标**：先以一张完整、精心设计、可反复交战的 3D 战场作为品质基线，但真实战场面积由战役和地形决定而非固定 MOBA 尺度；最多镜头能观察的区域与通过镜头平移/跟随可到达的区域，都能看见真正运动、接敌、使用各自武器、攻击、防守、受伤、溃退、战死和接受军令的士兵。
- **规模**：实际每场双方各有多少人由世界军籍和战斗部署决定，可小可大。**首版同时承载能力与性能压力验证**使用**双方各 512 名士兵（1024 名普通士兵）+ 玩家主角 + 带兵军官/坐骑/战车/攻城单位（额外计算，不得拿它们充当 1024 士兵）**。该压力案例不是千个静止模型、同一 NPC 的复制计数或画面外直接按公式清零。
- **性能**：**MacBook Air M5、Apple Silicon、本地实际运行稳定接近/达到 60 FPS (60 Hz 流畅目标)**，在大规模真正接战、指挥、投射、士气溃散、摄像机移动时持续成立。必须在真实目标硬件测量，不能用云端 headless FPS、空场画面、静态 1024 人截图、M1/其他 Mac 或截图脚本冒充 M5 通过。若尚未取得 M5 真机授权，标记 DEVICE_NOT_TESTED，不可宣称通过。
- **艺术**：不是追求近距离超写实 4K 电影人物。人物必须有真实可辨识的**头脸、手、武器、衣服/护甲、身体姿势**，动作可以清楚看出是在劈、刺、格挡、射击或逃跑。镜头拉近时能够辨识基本脸部与手部结构；拉远时以轮廓/兵器/旗帜/动作与队伍阵型识别。人物不能永远是球、柱、方块或无手无脸的简易图标。
- **剧情写作暂时全部留空**：Owner 将来独自创作正式剧情、人物对白、爱情、友情和权谋情节。**Codex/Dot/Pro 不得自行填写为权威剧情，不得为了实现战斗而强制编写剧情章节、固定人物命运或不可修改的故事。** 初版仅设一个可执行的军事情境/起始战役作为**唯一叙事树根、战场测试与游戏玩法入口**；在数据层预留以后从这条根逐步自然分岔的空间。**“唯一开头”不等于所有战争结局由玩家完全决定**：独立敌军、友军将领、战略形势和现实世界条件始终发挥作用。
- **核心优先级变更**：先把当前战场的操控、士兵真实性、兵种、指挥、任务目标、攻城和性能做好，再扩大陆地图和历史时代；不是丢弃原先长线愿景。

### 0.1 最新 Owner 修正：战场面积和真实军队数量不应锁死

**本条覆盖本文“地图必须 MOBA 尺度”“一场战役双方固定 512 名”的任何误读。** 见 `PRODUCT_DECISIONS.md §1L`：地图范围按照平原、山地、围城、追击和战役真实需要确定，可更大或更小，按需分区/流式加载；兵员数量来自世界真实军籍/部署，允许少量、几百、千人及更高规模。游戏必须支持**至少 1024 名普通士兵在同一战斗世界同时持续存在**的标准压力场景（512v512），**而不是要求每场 1024、同一屏 1024、必须全部同时近战或最多只能 1024**。远处可以更新率更低/队伍级聚合，但兵员身份、位置、战斗因果、伤亡和存档持续。首版聚焦一张精品河关是实施起点，不应成为设计上的硬面积上限。更多兵员受真实硬件承载能力约束，不宣称数学无限。

### 0.2 Owner 最新精确解释：软性局部容纳，军阵有实际厚度，局部模型可以重叠

`PRODUCT_DECISIONS.md §1M` v4.2 **覆盖此前严格实体互斥/完全不能重叠的方案**。用户说的是：脚下真实土地不能让很多士兵同时堆成同一点；但斜俯视时前后两名士兵看起来几乎重叠、两三名士兵紧密混战、模型肢体/脚步有小幅重叠都可合理。**目标不是逐人刚体互斥，而是限制过高局部密度，形成足够的阵型宽度、前后纵深和可信的军团体积感**。

建议继续用空间邻域网格，以局部占用密度/加权人数判断拥堵。少数贴近可通行与接战，随着局部人数增加平滑减速、缓和分离、外围等待/改路/重新展开；避免大量士兵同坐标重叠、突破城墙或永久卡住。马/车/冲车可以拥有较高占用权重和更明确的几何约束，城门/桥的容量由地形决定；**不要求每个普通兵的完整身体外轮廓与别人完全不相交**，尤其不能因为碰撞算法让玩家与敌将、盾阵、围攻失去正常的近距离战斗。不同高度/路径做合理处理，性能不能随全部单位两两检测而崩溃。

若千人军队在合理密度下无法铺开，扩大城门外集结场、侧翼/纵深战场或分梯队进场，不把既定军队全挤一个攻城口；局部堆叠必须先修，不能只放大地图掩盖。验收见 `ACCEPTANCE_MATRIX.md §7F-F`，少量可理解的视觉交叠**不是失败**。

## 1. 一张地图必须承载真实战争，而不是竞技 MOBA 的对称战线

### 1.1 地图

- **河关原型**可采用近似 MOBA 的操作视角，但战场面积不锁死为 MOBA 地图：有明确主通路、侧路、营地、丘陵/树林/高差、河道或桥梁、补给线、围墙/城门、城内/城外区域，但**不是抄袭现成 MOBA 的三路塔和固定刷兵**。尺寸由千人排布、骑兵冲锋、军官视野、攻城/侧翼调动的可读性确定；所有功能靠一张高质量图先打磨。
- 视角为斜上方 3D；WASD 操作主角、鼠标瞄准/攻击，支持移动镜头、跟随主角、观察局部战场和必要的有限战术地图。摄像机平移/拉近后，**当下视野里的单位继续真实战斗**，不能出现“镜头走过去人们才苏醒/假动作”的现象。
- 关卡提供有功能区别的地形：坡道/高处有射界与行军代价，桥/隘口影响纵队，城门/城墙改变攻防，树林影响视野/骑兵机动，补给线关系到长期胜负。视觉对象与碰撞、AI、战斗判定一致。
- 初期只制作**一张**精细、可重复用于遭遇战、野战、攻城、防守、截粮或救援的地图/地形系统。可以局部变体与地图预设，不要先堆十张粗糙地图。

### 1.1B 最新 Owner 补充：简化千人普通士兵 AI，以真实打斗观感和帧率为先

本节是 2026-11-12 的**直接用户决定**，优先于任何此前暗含“每名小兵必须有精密独立决策”的措辞。**每方至少 500 人、合计 1000+ 人、真实伤亡和 60 FPS 的目标仍不变**。

- 允许把普通小兵的行为智能降到简洁的**有限状态机 + 队伍级大方向**：队列/队伍服从、靠近局部目标、按武器距离/攻击方向/冷却发动攻击、格挡/硬直/受伤、士气下降、撤退/逃散或投降。每人可只持基本的阵营、血量、攻击/防御、武器/距离、士气、目标和位置等状态。
- **不要求**每名士兵建立完整的战术大脑、复杂个人意图/回忆、重度寻路、精细逐帧全身物理或一对一智能决斗；复杂战略决策集中在**将领、小队、已下达的任务**，小兵执行简单可见行为。
- 在**屏幕内**仍须让小兵有攻击动作、真正的命中或攻防判定、状态变化与可见结果。动画可以简洁、动作库可以共享并错开相位、命中模型可以简化，但**不能假互砍（动画没有实际作用）、永远打不死、录像表演、仅靠剧情瞬间结算**。
- 在**屏幕外/远景**允许低频或聚合的近似交战，保持可信队伍位置、伤亡总数、士气与命令，并在镜头转入时自然恢复个体动作与状态，不能无因恢复死亡者、重置士兵或突然改变战果。
- 若性能困难，**先降低普通士兵的思考复杂度、决策频率、远景动画骨骼/细节、独立寻路和物理开销**；优先保留 1024 人战场的打斗规模、镜头临近所见的手脸武器与动作、军令可信度、主角九种武器手感和实际帧率。
- 群体真实感可以来自兵种/装备/阵型、动作相位、打击反馈、士气/退却、将领指挥与任务结果，而不必一千个 AI 各自拥有高层策略。防止上千人只围着玩家一拥而上，队伍必须遵守基本战线/阵型与集火约束。

**清晰的取舍**：允许“简单而可信地打仗的 1024 名士兵”，拒绝“聪明却只能流畅显示几十名士兵”。此简化不降低主角与军官行为质量，也不修改真实 M5 60 FPS 仍需实测的验收边界。

### 1.2 真实千人同时战斗

- 目标是 **1024 名以上具有持续身份的士兵**：每个真实士兵有阵营、队伍/将领、位置、装备、血量/伤势、士气、当前命令、攻击目标/动画状态、伤亡/逃跑等。不能仅因镜头离开就删除其死亡/转移记录，也不能把所有军队替换成一个英雄护卫。
- 在当前画面可见的接战区域，近战单位须根据武器的有效攻击窗、朝向、距离与阻挡**真实命中、反击、格挡、受伤/死亡**；弓箭/弩有弹道/射界、装填与可见的射击。骑兵须有冲锋与受阻，攻城者有器械/城墙的互动。
- 在**同一场战斗**里，对镜头外仍在战斗的部队可以使用确定性的分层/聚合模拟节约 CPU，但必须保留身份与阵型/单位战损映射；镜头移动进入该区域时能**平滑、因果一致地还原正在进行的真实交战**，不产生无因复活、瞬间击杀、时间停止或不可解释的损失。近景永远不能只播放互砍动画却无实际伤害。
- 数量大时可以降低屏外单位的决策频率、屏内远处动画细节和模型层级，但**不能以直接暂停战斗/复制静态士兵/只让 20 人真的攻击**来达到帧率。
- 重视群体行为：列阵、随旗推进、接敌、后撤、冲锋、保持距离、侧翼受袭、受阻、援军、前排接敌、后排轮替、路口拥堵、受创溃逃、将领死亡后混乱。玩家应看到军队而不是一千个互相穿模的散点。

## 2. 不同兵种与装备

### 2.1 步兵/远程/骑兵/器械

至少要建立可实际派遣的武器类别，并允许同军队有差异化装备、护甲、训练与阵型：
- 刀剑轻步兵、枪矛兵、长刀重步兵、盾牌兵、棍棒/轻武装兵；
- 持弓弓手、持弩弩手；可根据训练、补给和装备使用对应射程/装填/穿透/压制行为；
- 骑马的骑兵（含持近战兵器的骑兵；未来可扩弓骑），与步兵真实互动，马匹不会被当作不受伤的速度加成；
- **战车**是初版必须可操作/可编组的作战单位或特殊战场单位；在中晚唐式物质文化中并非普遍主力兵种，使用须通过**架空军事设置、地形限制、牵引马匹/车体生命与速度/转向/地形成本**体现，不能凭空当成唐代典型冲阵主力；
- 攻城部队/器械：可使用攻城梯、撞门木/冲车、投射器械、工兵或适合该时代的设施；至少实现**可受损的城门/城墙防御节点、守墙与攻门的真实流程**，而非点击“攻城胜利”直接结算。攻城器械随时代/物资限制，初版暂不以现代火炮替代。

### 2.2 装备是实物

- 装备包括武器、盾牌、防具、箭矢/弩矢、马匹、必要的攻城器材；同类型装备可以存在品质、受损与数量差异，但首版不必无限制造装备稀有度等级。
- 士兵没有武器就不能凭空用长刀；没有箭矢就不能无限射箭。伤亡、缴获、回收和损坏接入现有 WorldSim 资源账本。
- 盾牌能从适当方向遮挡或格挡，穿甲与伤害根据武器、距离和护甲；重甲使角色承受负重或行动差异，战车/骑兵对枪阵、树林、城墙不能无视物理条件。

## 3. 玩家：九类必做的近战/远程装备与可操作战斗

**武器首次覆盖清单（不得偷偷删除或改成仅换皮）**：
1. 剑（单手）；
2. 刀（常规单手刀）；
3. 棍；
4. 枪（长枪/矛，突出刺击和距离）；
5. 长刀（双手/长柄重刀，宽挥砍与惯性）；
6. 弓箭；
7. 弩；
8. 剑 + 盾；
9. 双剑。

**此外初版支持骑马作战、战车作战或指挥**，应与武器系统协同，不只是地面速度按钮。

### 3.1 每把武器有自己的普攻与技能

所有武器必须拥有**明显不同的基础攻击节奏、攻击范围/扇形、重心、连招、起手/后摇、格挡/闪避能力和几项有意义的武器技能**。基础输入保持 WASD 移动、鼠标方向、左键普攻和统一技能热键（可重绑）；同一热键随当前武器切换实际技能与动作，避免全装备共用一个“魔法旋风斩”。

**可用作初版设计核验的动作差异（具体平衡由 Codex 反复测试优化）**：
| 武器 | 普攻特征 | 非魔法技能方向（可调，必须有差异） | 明显弱点/反制 |
| --- | --- | --- | --- |
| 剑 | 中短距离快速刺/削、节奏灵活 | 连刺、偏转、转身反击 | 破甲/对长枪阵困难 |
| 刀 | 近距离劈砍、斩击较重 | 连斩、破势、横切 | 被长柄武器保持距离 |
| 棍 | 长度适中、横扫与钝击 | 扫腿、推击、招架反震 | 对重甲/盾正面杀伤有限 |
| 枪 | 直线远距离刺击、方位要求高 | 长突、定枪拒马、连环点刺 | 被贴身或侧翼包围 |
| 长刀 | 较宽扇形、较慢蓄力 | 大范围重劈、破盾、借势横扫 | 起手慢，容易被快武器打断 |
| 弓 | 拉弓、瞄准、抛射/射程与箭囊 | 蓄力射、压制/速射、精准射击 | 近身压力，射界/弹药限制 |
| 弩 | 威力较高、发射快但重新装填慢 | 预装/瞄准、破甲射、掩护/机械连射（依器械合理性） | 装填空窗、短时间持续输出弱 |
| 剑盾 | 防护正面、短兵器近战 | 盾击、持盾推进、格挡反击 | 重型破盾/绕后/长时围攻 |
| 双剑 | 高频连击、灵活但护盾缺失 | 双向斩、交叉反击、快速脱离 | 对枪阵/大盾/密集远射脆弱 |

- **动作和判定同步**：刀实际挥出的方向与伤害轨迹一致、枪尖接触才算刺中、盾与方向有关、箭矢可见、弩必须重装。禁用“视觉上刚起手、远处敌人就掉血”的廉价表现。
- 角色初期大致一敌二，后期高水平角色能凭攻击、技能和机动在千人战场中**累计**消灭许多散兵，但**生命值上限受限、十数人有效合围与齐射可致命**；不能通过增加十倍 HP 来假装成长。
- 射箭与弩射可以通过瞄准辅助/目标高亮提高操作体验，但不得自动追踪敌人穿墙锁头。
- 角色在骑马/下马、持盾/换武器时应有合理的转场动画和操作限制。战车可操控但受驾驭/车体状态和地形制约。

### 3.2 手感优先

- 位移应清晰可控，有加速/转向/冲刺/必要体力限制但不黏手。不同武器轻重有差别，不把每次攻击都做成僵硬站桩。
- 提供命中反馈（武器接触、方向性受击、闪避/格挡声、轻微镜头反馈、适度血迹/伤势/倒地或战斗失能），避免夸张飞天/魔法效果。
- 可以有可配置的轻重击、锁定/非锁定、辅助视角与输入缓冲；但**不能让 UI 或镜头比战斗更难操作**。初版严格保留鼠标瞄准而非点击移动。

## 4. 统军：战前下达任务、阵中令旗号角、将领自主执行

### 4.1 战前部署与任务派遣
- 初版即可在准备阶段给军官和所辖部队安排**作战任务**：占领/坚守关键地、截击/保护补给、守城门/攻城门、牵制/包抄、警戒、支援某个将领、预备队待命。结合人员、装备、补给和真实位置检查是否合法；不是固定 MOBA 预设线路。
- 每支部队/军官拥有身份、约定目标、命令和所辖队伍。战斗中其执行可因侦察、敌情、伤亡、士气、道路被堵或军令到达而调整；军官有**有限情报与自身行为逻辑**，不是预先录好的路径。
- 不同的兵种应知道适当站位，例如盾兵前列、弓手后列、枪兵拒骑、骑兵侧翼；但可被环境打乱。

### 4.2 指挥工具
- 近处可用**令旗、号角、直接口令**指挥能合理看到/听到的队伍；旗号/鼓角具备真实范围与事先约定的语义，不是屏幕上远程瞬间控制整个地图。
- 远距离、复杂命令通过**有真实路线与时间的传令兵**派送，也可通过实际的军官指挥链传递；可能被截获、丢失、误解、拒绝，超时不保证玩家能立即知道失联原因。
- 将领可以按已发任务自主组织、变阵、等待、援救、撤退或抗命，玩家不是必须点选 512 个士兵逐一下令；也不能“点一个命令后将领 AI 自动把一切都办好”，玩家仍应有战术决策与救险窗口。
- 显示可合理获得的命令状态：草拟、派发、传递中、已确认、执行中、超时未回报、拒绝/失效；不能泄露玩家无法获知的敌方截令细节。关键命令输入在动作中要直观、少层级、可快捷发出。
- 可暂停查看已知信息/部署界面作为设计默认，但暂停时不能凭全知知道远方敌人准确位置；速度/时钟遵守同一世界规则。

### 4.3 2026-11-12 最新 Owner 决定：双方高级将领与分层统帅（LOCKED）

**这是首版战斗重要组成部分，不是等到大地图/剧情才加入的远景功能。** 详细本人裁决见 `PRODUCT_DECISIONS.md §1H`。

- **双向对等的军事能力**：敌军和友军都有真正能作战的强力主将、副将与分队军官。全军主帅（军队的总体负责人）与战场主将（具体指挥本次会战者）可以不同；高层主帅通常有护卫、中军/营地、城内或远离战线位置，有时不进入当前场景。全军主帅**不能默认每次刷新在地图中间供玩家击杀**。
- **强者不应只是加生命值的普通兵**：可用玩家已有九武器的动作/受击/防御基础，扩展给双方高级将领；需要掌握实际攻击、格挡/闪避/反击、合理突进与脱离、武器距离、冷却/体力、对不同敌人的威胁判断。强力将领按身份/经历/装备和状态区别，不是每名普通分队军官都必须与玩家同强。
- **一当数十与强将对抗同时成立**：玩家在适当阶段/条件下可以凭更强的连击、范围压制、精准走位与装备，在一场战斗中击倒数十名普通士兵，不应因为这种能力就把所有敌方普通兵改成高 HP 精英怪。与此同时，敌方强力将领也会独立攻击并击杀**友方普通兵和将领**，玩家分神清小兵时，己方战线可能被敌将打穿。双方强将交手像高水平 MOBA 对抗的**操作/技能博弈**，但不强制 1v1 决斗副本、不引入无根据的魔法攻击、无敌血条或强制锁定镜头。
- **自主行为与有限认知**：高级将领可选择率兵突破、防守关键点、掩护溃军、保护主帅、冲击敌方将领、避战保存实力、增援薄弱战线或临时改令；取决于已知情报、任务和实际兵势。友方非主角将领也应有能力自主杀敌和影响胜负。敌将不必每次主动冲向玩家，不以“英雄互殴”取代大战。
- **保护/负伤/救援**：主帅、主将与高阶将领可能受伤倒地/失能、被近卫保护、被担架/随员救离危险区，亦可能撤退、被俘、投降或真正死亡。救援有实际距离、人员、时间、风险和军心代价；成功救护仅对**仍然活着**的伤者有效，不允许悄悄复活已死亡者。战后其伤势、指挥能力与去向影响世界记录。
- **指挥链断裂与继任**：主将/统帅失能、失联或被俘后，部队不是立刻全部死机。既定军令可继续，副将/备选统领可依法/按关系/局势接替，但接令时间、威望、联系、士气、军纪和协同效率可能变化；可能出现局部溃散，也可能保持阵线、战略撤退、降服甚至反击。阵亡军官仍计入军籍/伤亡，不拿 1024 个普通兵名额冒充。
- **独立主帅的抽象实现**：即使首张地图规模限制无法表现真正的远方大营，必须在一场战斗的**阵营军令与任务状态**中表示“主帅在场/不在场、指挥权、命令来源、通信时延、继任/失联”；不应强行让敌方全军统帅肉身出现在屏幕上才有指挥系统。

### 4.4 战斗与操作的要求

- 主角和敌方强将真实交手有可读的攻击准备、方向/射程/判定、命中/格挡/闪避、技能冷却、受创硬直和可利用反制窗口。不会靠隐藏护盾或读玩家按键作弊。
- 如果主角忽略敌方将领、专砍普通敌兵，**敌方将领也在攻击/调兵，使己方发生真实伤亡或目标丧失**；如果主角追敌将，己方也会继续执行已发任务，敌军其他将领也不会停止战争。
- 同一位敌将不是固定“首领血条与关卡终点”：可受命防线、临时转移、被其他友方将领击伤/击杀、被护卫救起或撤走；游戏必须在敌将**不被玩家亲手杀死**时仍能自然产生不同结果。

## 5. 战争胜负：不是双方互相杀到零

**以真实战役为参照，允许多种合法胜负与中间状态**：
- 夺占/守住关键地形、城门/城墙、军旗或补给线；
- 在限定时间内阻挡、突破或撤退，护送辎重/传令兵/难民；
- 敌军因士气、军阵、指挥层、伤亡、补给受损而**主动退兵、溃散、投降或谈判**；
- 一方完成突围/救援/切断后勤，达成军事目标，即使敌军主力尚存；
- 城池因被包围、失去补给、守将降服、内应开门、城门突破而失守；也可以解围。
- 主角战死结束当前人生；主角未死、己军败退或被俘不一定 Game Over。局部胜负的评分不能掩盖真实伤亡和仓储。
- 战役目标应由战前军令、地理与世界局势定义；不要因玩家明显成功就临时提高隐藏阈值制造强制败局。
- **初版唯一游戏开场**可以定义一个中性的边境战场/城池军令入口，由不同任务方案产生战果分支；**正式文学剧情全部留空**，由 Owner 后续自行创作与加入。主线不是由玩家随意点击“成为皇帝”，世界约束与 NPC 行为仍能迫使局势发生变化。

### 5.1 2026-11-12 最新 Owner 决定：胜负必须由战场态势因果决定（LOCKED）

旧的“敌军伤亡/逃离达到固定比例就宣告败北”只能作为**编队战力或士气变化的输入之一**；不得单独成为全类型战斗一刀切的硬通关规则。即使敌方主将或几乎所有高级将领死亡，也不能**仅凭人物击杀**直接自动结算胜利。

至少综合考察：
1. **战略目的和战术任务**：攻守城门与城内要点、护送、突围、阻援、保粮、占地、守时、保存主力、争取增援等；双方目标可以不对称，局部战果不等于战争终局。
2. **实际战力和态势**：双方仍可作战的有效兵力与兵种/装备/训练，主角与高级将领的实战作用，士兵伤亡/负伤/疲劳，阵型是否稳定、包围/侧击和地形优势。
3. **组织和心理**：主帅/战场主将/副将的可用性和实际指挥链、士气、近卫与旗号、预备队、撤退路、部队凝聚力和能否接收到正确命令。
4. **后勤与外部条件**：粮草/箭矢/器械/城防、援军时间与位置、天气/视野/实际地形、预定的敌我战略计划与允许的战场时间。

结果可包含**明确达成目标的胜负**、双方撤退、局部失地但主力保存、溃败、投降、陷入僵局、继续围城或战略撤回；不强求每次打到一方死绝。

**主帅/主将死亡的条件性影响**：
- 组织脆弱、阵地不稳、士气低、退路不畅且无继任者时，指挥官死亡可引起真实连锁溃退和投降；最终胜利是**军队真实失去抵抗能力/目标**的结果。
- 若副将成功接任、地形易守、命令已下达、士气高或援军尚在，主帅死亡后也可能继续抵抗甚至击败敌方；不允许“阵亡主帅后全图刷出胜利 UI”。
- 反之**不杀主帅也可以赢**：夺关/切粮/解围/护送/援军抵达或迫使对手撤退都是合法战果。
- 如果玩家本人战死，**当前人生按产品规则结束**，但必须记录当时世界与部队仍在的客观状态，不能用“玩家 Game Over”推导出“敌方军队立刻赢得整场战争”。

正式文学剧情仍留空；这套胜负评估是可测试的军事状态逻辑，后续作者剧情可使用但不能绕过。

### 5.2 新增 Owner 战场广度：先锋/叫阵、不同地形、粮水交通与跨时代战争（2026-11-12）

**最高正式来源**：`PRODUCT_DECISIONS.md §1I`，战役系统细则与设计/分批实施见 `BATTLEFIELD_VARIETY_AND_FORCE_ROLES_20261112.md`，测试见 `ACCEPTANCE_MATRIX.md §7F-C`。

- 双方不只“普通兵/基层军官/主帅”三层：有**先锋/前锋将领、叫阵小将/斗将、老兵精锐、近卫、不同兵种的统带将领**。先锋率队开路、侦察、试探或冲锋；叫阵小将强于普通兵但不一定有高层指挥权，可挑战/试探/撤退，被击杀或拒战不应直接判胜。敌我均应有多样化战斗力与兵种组织。
- **必须支持可玩多样战事**：平原正面对阵，复杂高差/河桥/隘口正面战，夜间偷袭，包围与突围，守营/守城/攻城，山地/丛林战，伏击与绕道，争夺多个据点和不同城池。每类要有独特战术、情报、地形和任务后果，不能做成换名字的同一张两军互冲地图。
- **重要据点与物资通路真实存在**：粮仓—运输道路/河道—桥梁—营寨—前线的粮、箭、马料；水源/水井/渡口及取水交通；切断/修复供应链和占据不同城池影响军心、行军、援军及战力，不即时清空任何军队。至少多据点争夺不只一个关键圈。
- **额外战争方式**：火攻与防火、投石车/攻城器械、工事机关与陷阱；兼顾风雨/火势/地形/器械位置、战损与反制。**水战、海战、火炮**是重要的历史灵感与潜在后续可玩方向；是否实际开发独立系统取决于乐趣、成本和技术演进。**不要求玩家管理舰队全部物资、炮弹或工业细节**；若选用，以清楚易懂且有效的简化规则表现。
- **技术时代和实施顺序**：游戏初期的中晚唐式战场以冷兵器、投石、早期攻城设施和舟船/河战为主；成熟火炮和近代海战在之后满足工业/技术条件才出现，不能无因穿越科技。Codex 可先使用现有一张高质量河关地图作为多地形与多任务验证平台，逐步扩展真正不同的场景，不必立刻批量制作粗糙空地图。**这些历史要素不再是逐项必须实现的目标**；应按可玩性与成本筛选、简化、合并或舍弃，已锁定的核心千人战斗与操作质量不因此降低。
- 继续遵守双方强将、玩家可在合适时机一当几十、重要将领有护卫/救援/继任、战役胜负由实际力量对比和目标而非固定杀人数决定，以及普通士兵可轻量 FSM、M5 60 FPS 仍待真机的规定。
- 正式剧情、固定人物与对白仍由 Owner 自己创作；当前只设计战争机制、任务/地图数据与无文学剧本的可玩场景。

### 5.3 新增研究范围：唐末至清朝战史不能只当地图背景

用户已要求从唐末、五代、宋辽夏金元、明、清前中后期的真实战役全面筛选适合游戏的**战术、地形、单位、装备与器械**。权威史料/战例初稿：`docs/HISTORICAL_BATTLES_TANG_TO_QING_RESEARCH_20261112.md`；Owner 决策见 `PRODUCT_DECISIONS.md §1J`。每种战役的独特作用须落在真实地形/军令/后勤/兵种/胜负状态，而非仅改服饰、名字或固定结局。

**明确纠正**：宋元已经发展火药军器及早期火铳，明清有多种火枪/火炮，成熟近代工业舰炮与蒸汽/铁甲舰才在晚期产业条件满足时解锁。投石器械的“炮”与管状火炮分属不同技术。研究期分层不改变当前唐式初始战场与已决定的战斗初版目标：仍优先精修一张千人战场、敌我强将、九种武器和 Mac M5 60fps 实测，后续扩充可复用历史战役模板与海陆军械发展。

### 5.4 最新 Owner 简化裁决：历史元素只为好玩服务

`PRODUCT_DECISIONS.md §1K` 已明确覆盖 §5.2/5.3 中“每种历史战役都要做/历史要素越多越好”的潜在误读。优先保证玩家能**自然地战斗、观察战线、使用少量军令和把握几个关键目标**。桥梁/山地、伏击、后勤、水战、火炮、海战、投石和陷阱是**有选择地使用的玩法参考**，不是首版或完整游戏的强制逐项任务。系统可在后台简化运算、自动委派将领和后勤；前台只提供少量有意义、因果可理解的决定。只有明显提升乐趣且不明显拖累性能/开发质量的机制才纳入真实实现。

### 5.5 新 Owner 决定：士气与战斗强迫性、全歼/溃逃/战略撤退/投降（LOCKED）

`PRODUCT_DECISIONS.md §1N` 和 `docs/BATTLE_MORALE_COMBAT_COMMITMENT_AND_OUTCOMES_V1.md` 是本节完整权威。

战争可以通过四种主要军事结果结束：**全歼（全部杀死）、溃败逃散（玩家决定追击或停止）、有序战略撤退、投降/降服**。原有夺点、守城、护送、救援、突围等任务目标继续有效，可以在敌方仍有大量幸存者时取得局部战术胜利；战报必须准确区分阵亡、逃散、投降、被俘、撤出与存活，不能混为全歼。

**两个独立指标：**
- **士气**：影响部队有效战力、阵型、命令执行/服从及逐渐变化的忠诚/离队倾向。重大伤亡、斩杀重要将领、敌强我弱、突袭、包围、退路/粮道被断、重要目标失守会降低；继任、援军、整队、鼓舞、成功任务可以恢复。士气到零，部队会尝试逃跑、弃械、投降或失去组织，但按小队/消息传播渐进发生，不是全军同帧同步。
- **战斗强迫性**：权威/合法性（包括本地首府/政权威望）、军纪、使命重要性、指挥链与副将继任、退路和投降选择共同形成的“是否有足够权力/动力支撑继续作战”。它不是攻击力加成，也不等同士气。高强迫性可使低士气部队继续守阵、执行命令或有序撤退，但不能凭空恢复战斗效率。

**主帅阵亡的差异**：首府/政权威望高、军令合法且副将接任明确时，部队可能认可继任者而继续作战，不因斩首逃跑；无继任、权威弱、士气低且被包围时才可能连锁溃散/投降。主帅可以自主判断继续战斗、组织撤退、逃跑或投降，不能只看一个固定阈值。

**追击选择**：敌军溃逃后，玩家可以追击以增加俘虏/伤亡/缴获，也可以停止追击、收拢部队和完成原目标；追击存在疲劳、队形散乱、后卫反击/伏击风险。有序战略撤退保留指挥链、后卫和主力，不得与无序溃逃混为一谈。

实现应复用 `battle.gd` 的士兵士气、`field_objectives.gd` 的有效战力/崩溃计数、`officer_corps.gd` 的副将继任，增量补足独立战斗强迫性和结局决策；普通士兵仍使用轻量 AI，玩家只面对简单的追击/停止选择。详细验收见 `ACCEPTANCE_MATRIX.md §7F-G`。

### 5.6 新 Owner 决定：共享兵种属性，分队级士气，军队级强迫性（LOCKED）

**权威：`PRODUCT_DECISIONS.md §1O`。** 普通士兵不应每人独立拥有攻击力、防御力、护甲和士气。按层级共享：
- **兵种/装备模板**共享基础攻击、防御/护甲、武器伤害/射程/攻速、移动速度、最大生命等静态战斗属性；同一批同装备同训练士兵引用同一模板。
- **整支军队**共享大量数据：基础士气、战斗强迫性、首府/政权威望、军纪、使命、整体补给与指挥权威。
- **分队/编制**是普通兵动态士气、凝聚力、疲劳、局部伤亡比例、当前命令和接敌压力的主要粒度。不同地点遭受不同冲击时，先更新相应分队，其他分队通过目击/旗号/号角/传令后再更新。
- **单兵**只保存必要的身份、分队/模板引用、位置、朝向、当前动作/轻量 FSM、必要的当前 HP/伤势/死亡/俘虏/逃散，以及确实不同的装备/弹药。基础攻击/防御/护甲/最大生命从共享模板读取；同批库存可按批次保存。
- 不要随机生成每名普通兵的独立士气，不要每次受击都逐人扣 morale；也不要把同批基础攻防数值复制到每个 Unit。主角和重要将领可以保留独立能力与状态。
- 共享属性绝不等于共享血条：近景仍逐人受击/死亡，远景可按批次模拟，但人员、装备、伤亡、俘虏和存档守恒。

详细合同：`SIMULATION_CONTRACTS.md §9G`；验收：`ACCEPTANCE_MATRIX.md §7F-H`。实现以 Godot profiling 为准，不强制 ECS。**当前代码已存在逐兵 `Unit.morale` 随机初始化和逐击扣减，Codex 应将普通兵士气迁移到分队级，并评估把复制的 armor/静态攻防属性改成共享 profile 引用；保留必要的单兵 HP/死亡状态和旧档迁移。**

## 6. 画面与声音质量：看得见人在打仗

### 6.1 单位美术最低质量线
- 所有可接近观察的人物要有可分辨头脸、两只手、上身衣料/甲片、两腿/脚、实际持握的武器和有效姿态。兵种从剪影能辨识，不只是不同颜色的圆柱；脸部可保持简洁 stylized/低多边形，但要真有人形与基本面容。
- 服装/甲胄/装备依职业、财富与物资实况有区别，色彩与设计参考**中晚唐式架空军队**，不必像 AAA 人脸，但不能劣质占位几何体直接当正式版。
- 近处/关键交战提供成套的攻击、受击、招架、死亡、奔跑、射箭、换弹、骑乘与攻城动作；远处可简化骨骼/动作细节，但**不能静止**。军阵旗帜可辨、箭矢与投射物符合方向与遮挡。
- 视觉效果克制：脚步尘土、合理兵器击打音、号角与战鼓、战争环境声和适量状态反馈；大型交战不应只有一千个重复的同步摆臂动画。使用随机动作相位/战场情境变化，不破坏真实命中时机。
- **关键逻辑**：正常斜俯视远景不可能在同一屏同时清楚看见 1024 张脸；必须通过**镜头可拉近及局部观察**验证脸/手/兵器/衣服的可辨性，拉远通过阵型和旗帜验证可读性，不能一边要求全军同屏一边要求人人面部特写。

### 6.2 画质与性能优先顺序
1. 真实战斗与命令；
2. 60 FPS 交互流畅及输入延迟；
3. 人物/动作/装备的清楚可辨；
4. 地图、地形、城池、战场材质、光影、声音的完整性；
5. 更贵的特效细节与非核心装饰。

优先维持角色清晰与战斗信息，而不是给一千人都加昂贵的复杂毛发、布料物理或独立实时阴影。

## 7. 性能与引擎：做足优化，但不能拿优化当作弊

### 7.1 目标设备与清晰度
- **目标设备**：用户的 MacBook Air M5（Apple Silicon、无风扇设计），以其真实内置显示器和用户外接 4K 显示器作为验证配置。屏幕刷新率 60 Hz 时的游戏目标为**持续流畅的 60 FPS**，不是只在第一次载入时截一张 60 FPS。
- 可以使用稳定的高质量分辨率缩放/上采样和可调阴影/光照/动画 LOD，但必须在**屏幕最终输出分辨率、实际内部渲染比例、画质预设**中如实记录，不可用 720p 结果冒充原生 4K。
- 建议在**连续 ≥20 分钟的 512v512 真实交战**中实测帧时间、FPS、掉帧、峰值内存、温度/功耗可读值、镜头快速平移、攻城/骑兵突击/高密箭雨。理想持续目标：FPS 中位数接近 60、P95 帧时间尽量 ≤16.7 ms、明显卡顿（如连续 >33 ms 帧）不得频繁出现；**基准是硬目标，未在 M5 实测不标 PASS**。
- 需要真实可交付版本在用户 M5 上验证；授权前不得远程操作该电脑或假称已经真机通过。没有 Mac M5 时可先运行云端 macOS arm64 图形/性能探针，但报告必须标注是代理设备。
- 对可控硬件限制可实现 Performance/Quality 可选配置；**不得默默把 512v512 降为 100v100 或把场内士兵换成不会真正作战的布景来报告完成**。若达不到性能，在 PR 中公开指标、瓶颈、已试优化和后续改善方案，继续尽最大可能优化，最终是否修改要求须由 Owner 决定。

### 7.2 可选技术路线（工程建议，不是用户指定实现细节）
- 现有项目 Godot 4 / GDScript 优先保留。优先做实测型技术 spike，**只有证明明确瓶颈且替代方案在相同画面/战斗上更优**，才提换引擎/大重构。
- 先 profile 再优化：CPU AI/pathfinding/避碰/攻击判定、GPU draw calls/像素填充/阴影、骨骼动画、场景树开销、物理查询、内存和资源加载均分别记录。
- 用**队列/将领层决策 + 局部士兵行为**、空间网格/邻域检索、分层导航、按帧预算与错峰更新，避免 1024×1024 全体两两距离检查；能继续战斗的兵不能因为性能优化而丢弃状态。
- 远近模型 LOD/动画 LOD/遮挡剔除，近景维持攻击碰撞精确与动画细节；GPU instancing / MultiMesh 或适当的 GPU 顶点动画只在兼容实际蒙皮/多姿态表现时使用，**不要假定 MultiMesh 自动支持一千个独立骨骼动画**。
- 将世界模拟、个人战斗判定与表现/摄像机分离：逻辑使用可审计、确定性/可重放的有限时间步，渲染以 60 FPS 插值；视野外可降低表现成本，**不可删除现实发生过的攻击或伤亡**。
- 在不同规模做性能曲线：20v20（旧回归）→ 100v100 → 250v250 → **512v512**。**前面的级别都是性能与功能中间门槛，不是可以宣布初版已完成的替代品**。

- **所有非设备专项通过**且可在真实 macOS Apple Silicon 打包运行，真实 M5 性能达标并获得必要的人类试玩质量检查后，才称达到**Owner 期望的战斗初版**。
- 如果实现功能但 M5 FPS 未达标，可以发布“工程候选/实验版本”，不得偷换成最终初版已达标。玩家主观手感尚未验证时，不称“消费级优秀战斗体验完成”。
- **剧情不计入此阶段验收**。不强制用户先设计人物/台词，也不能用未完成剧情阻止 Codex 的战斗开发。只有中性背景、军令和游戏目标作为必要文字。
- 旧 20v20/三城/少年从军代码、世界状态、存档、测试资产全部保留；如 PR #10/字体问题未解决，Codex 应按现有真实分支诊断、保留证据和修复，不重新实现旧功能。
